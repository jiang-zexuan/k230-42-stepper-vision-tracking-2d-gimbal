## 本项目解决的问题

PC 串口发来的数据并不天然等于一条“消息”：一次 DMA 空闲回调可能只得到半帧，也可能同时得到两帧。P03 用 PC 模拟视觉模块，先把接收、组帧、校验、恢复和通信状态这些问题独立验证，再在 P08 连接真实 K230。

## 代码到意图

| 代码动作 | 工程意图 |
| --- | --- |
| `HAL_UARTEx_ReceiveToIdle_DMA()` | UART 收到字节时由 DMA 搬到内存；线路空闲或 64 B 缓冲区满时通知程序处理这一段字节。 |
| `HAL_UARTEx_RxEventCallback()` | 回调中只复制数据到邮箱并立即重启 DMA，把耗时的解析和打印留在主循环。 |
| `VisionFrameParser_Feed()` | 每次只消费一个字节并保存解析状态，因此半帧下次可继续，粘包能连续产出多帧。 |
| `VisionFrame_Crc16Modbus()` | 对版本、长度、序号和负载计算 CRC16/MODBUS；只有接收值相同才更新最新有效帧。 |
| `CommunicationWatchdog` | 仅完整且 CRC 正确的帧刷新计时；没有有效帧时分别显示 waiting、active、timeout。 |
| `FrameSequenceTracker` | 观察 8 位序号的跳号、重复和乱序，提示接收端可见的异常但不武断归因。 |

## 本轮协议

```text
AA 55 | version | payload_len | sequence | payload | CRC16/MODBUS
```

- `version`：固定 `0x01`。
- `payload_len`：0 到 48 B。
- CRC 覆盖从 `version` 到 `payload` 的全部字节，不包含帧头；CRC 低字节在前。
- 示例：`AA 55 01 01 01 10 50 44` 是序号 1、1 B 负载 `10` 的有效帧。

## 复习要点

1. DMA 解决“搬运字节”，IDLE 解决“本次暂时没有新字节”，协议解析器才解决“哪几个字节构成一帧”。
2. CRC 不会修复数据；它让接收方拒绝无法证明正确的数据，避免错误目标进入后续控制。
3. 解析器是一个显式状态机：等帧头、读版本、读长度、读序号、读负载、读 CRC。状态保留在结构体中，因而能跨 DMA 回调工作。
4. 1000 ms 是 P03 的观察参数，不是最终云台安全阈值；P08 要结合真实 K230 帧率和实测时延重新确定。

## 学习问答

### CRC 如何确认前面数据没有损坏？

发送端先对约定范围的字节算出 CRC 并附在帧尾；接收端收到同样的字节后再算一次。两个结果相同，表示这帧通过该 CRC 的检错规则；不同就拒绝该帧。它不能数学上保证绝对无错误，但能高概率发现传输中的常见错误。

### 数据错误会在哪里出现？

可能发生在 PC 或模块生成数据、UART 发送、电平/线缆受到干扰、接收采样，或软件缓冲区溢出等环节。CRC 只能说明“收到的字节与发送方计算 CRC 时的字节不一致”，不能仅凭一次 CRC 错误确定是哪一段造成。

### 为什么 DMA/IDLE 的一块数据不等于协议帧？

IDLE 只表示 UART 暂时空闲，不知道发送方协议边界。发送方停顿可能把一帧切成两块，连续发送也可能让两帧落入一块。流式状态机逐字节找帧头、按长度读完并验 CRC，才给出协议帧边界。

### 为什么有些项目把固定块 DMA 改成逐字节 UART RX 中断？

当协议是不定长、间隔不可预测且项目没有准备好环形缓冲和流式解析时，逐字节中断的控制流更直观：每来一个字节就交给状态机。它不是 DMA 天生不可靠，而是在低速、不定长报文场景中用 CPU 开销换取实现简单、边界清楚。P03 已证明 DMA 也能处理半帧和粘包，条件是解析器与缓冲策略正确。

### DMA 和中断分别适合什么？

大块、连续、高频数据适合 DMA，例如 ADC 采样、显示刷新和连续串口流；低速、短小、事件稀疏或调试期的不定长数据，逐字节中断通常更容易实现和排错。二者都仍需要协议解析与缓冲设计。

### 粘包、半帧、重同步、超时和序号分别有什么用？

半帧和粘包描述接收分段与协议帧不一致；流式状态机解决它们。重同步在垃圾字节、版本或 CRC 错误后重新寻找 `AA 55`。超时表示长时间没有有效帧，避免将陈旧目标继续当作新目标。序号显示跳号、重复或乱序，帮助定位链路或缓冲压力，但不能单独证明错误发生位置。
